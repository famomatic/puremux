# puremux 전체 코드 감사 — 2026-09-06

> 수정 상태: 재현된 결함과 추가 후보·개선 항목의 처리 결과는 [수정 보고서](AUDIT_FIXES_2026-09-06.md)를 참고한다. 아래 본문과 실패 로그는 수정 전 commit의 역사적 감사 기록이다.

대상: `2fb0dd1340f25304a264d53ff8ec39e4944e91eb`, v0.2.3 출시 후 현재 작업 트리. 작성: Codex `/root`.

**판정: 수정 필요.** 경계 조건, 동시성·취소, 오작동, 기능 누락과 성능을 점검했다. 24개 top-level 재현 테스트에서 **22개 문제**를 확인했다. TS null/duplicate 사례는 동일한 continuity 검사 문제로, AAC 입력/출력의 채널 수 문제는 동일한 매핑 문제로 묶었다. HLS/DASH의 공통 시각 오차는 한 테스트의 두 subtest다. 제품 코드와 기존 테스트는 수정하지 않았다.

기존 감사의 해결된 항목을 재등록한 결과가 아니다. 예를 들어 예전 MP4 seek 시각 오차와 현재 실패한 seek의 커서 손실은 다른 문제이고, 이전 enforcer 버퍼 고갈과 현재 presentation synthesizer의 무제한 보관도 서로 다른 단계의 문제다.

**검증 범위와 한계**

- MSYS2 UCRT64에서 기존 전체 `CGO_ENABLED=0 go test -count=1 ./...`, `CGO_ENABLED=1 go test -race -count=1 ./...`, CGO 없는 `go vet ./...`, `go build ./...`가 통과했다. gopls는 올바른 workspace를 인식했고 진단은 없었다. 제품의 `C`/`os/exec` import는 발견하지 않았다.
- 추가 테스트는 `F:/cache/puremux-audit-20260906`의 Go overlay로 실행했다. **CGO=0과 race 계측 모두 24개 테스트가 의도한 assertion에서 실패**했다. 이 실패가 현행 결함의 증거다. build 실패나 테스트 준비 실패를 결함으로 세지 않았다. 두 로그에서 `WARNING: DATA RACE`는 없었다.
- 실제 OOM이나 사용자 파일 손상을 유발하지 않았다. 메모리 증폭은 10만 샘플 및 1천 AU로 제한했고, 파일 이동은 테스트가 만든 임시 디렉터리 안에서만 실행했다.
- 컨테이너·코덱 사례는 기존 사양 기반 fixture, 직접 유도한 필드 및 오류 주입을 사용했다. AAC/AV1/TS는 MSB-first 필드, MP4 count는 big-endian, Ogg granule/OpusHead는 little-endian이다. 압축 payload는 불투명하게 취급했다. 완전한 영상·오디오 디코딩이나 실제 플레이어 청취 검증은 하지 않았다.
- 이 감사는 발견한 문제의 근거를 제공한다. 모든 입력·스케줄에 대한 무결함 증명이나 새로운 전체 fuzz 캠페인은 아니다. 아래 정적 후보는 재현 확정 항목과 구별한다.

**F01 — 출력 디렉터리를 일반 파일로 교체한다.**

위치: [remux.go:350](../pkg/media/remux.go#L350), `installRemuxOutputWithRename`.

첫 rename이 실패하면 목적지의 존재만 확인하고, 파일인지 확인하지 않은 채 backup으로 옮긴다. `existing.mp4/` 디렉터리를 목적지로 주면 디렉터리 전체가 `.puremux-backup-*.tmp`로 이동하고 원래 경로에는 새 미디어 파일이 생긴다. 디렉터리가 비어 있지 않으면 마지막 backup 제거에서 오류가 나지만 이미 경로는 변경됐다. 비어 있다면 디렉터리가 사라진 채 성공할 수 있다.

재현: `TestAudit20260906OutputDirectoryPreserved`. 설치 오류 반환 뒤에도 `existing.mp4`가 일반 파일이 됐다. 원래 내용은 backup에 남으므로 영구 삭제와 구분해야 하지만, “실패하면 기존 출력 보존” 계약은 깨진다. 수정: 일반 파일 여부와 symlink 정책을 먼저 검증하고, 디렉터리·특수 파일에는 replacement fallback을 적용하지 않는다. 예: `if !info.Mode().IsRegular() { return ErrInvalidData }`.

**F02 — 입력 trun의 count가 메모리 상한을 우회한다.**

위치: [fragment.go:214](../internal/format/mp4/fragment.go#L214), 특히 샘플별 append.

`trun`이 duration/size를 tfhd/trex에서 상속하면 각 샘플의 명시적 필드가 없어도 된다. 따라서 작은 count 필드만으로 반복문이 큰 `rd.fragments`를 만든다. 입력 파일 길이·Open의 읽기 바이트 상한은 이 확장을 제한하지 않는다.

재현: `TestAudit20260906TrunExpansion`. 본문 `00 00 00 00 00 01 86 A0` = version/flags 0, big-endian count 100000. duration=1024, size=1 기본값에서 8바이트가 100000개 엔트리, backing capacity **5,775,360바이트**로 확장됐다. uint32 최대 count나 OOM은 실행하지 않았다. 수정: fragment/전체 샘플 수와 메타데이터 바이트 예산을 검증하고, count에 비례하는 할당 전 sample data 범위도 확인한다.

**F03 — PTS 재정렬 큐가 비화상 AU를 무제한 보관한다.**

위치: [ptssynth.go:108](../internal/preprocessor/ptssynth.go#L108), [ptssynth.go:236](../internal/preprocessor/ptssynth.go#L236); public 진입점은 `LiveMuxer.WriteVideo`.

reorder mode에서 큐 선두가 picture이면 뒤의 picture 개수가 lookahead를 채울 때까지 멈춘다. 이때 SPS/PPS/SEI 또는 파싱되지 않는 AU가 계속 오면 전체 `win` 길이 상한이 없다. `ptsProbeMaxHold`는 시작 probe에만 적용되고, public `MaxBufferPackets`와 `MaxInterleavePackets`는 이 단계보다 뒤에 있어 막지 못한다. `picCount()`도 매번 커진 큐를 순회한다.

재현: `TestAudit20260906ReorderNonPictureBound`. 기존 IPBB POC fixture로 reorder 상태를 만든 후 non-picture AU 1000개를 공급하자 **1004개**가 보관됐다. 수정: probe 이후에도 전체 AU 수·바이트·대기시간 상한을 적용하고, 상한 도달 시 명시적인 fallback/drop/error 정책을 사용한다. picture count는 증분 관리한다.

**F04 — 정상 TS stuffing/duplicate를 continuity 오류로 거부한다.**

위치: [mpegts/reader.go:167](../internal/format/mpegts/reader.go#L167).

모든 payload PID에 `CC == previous+1`을 강제한다. PID `0x1fff` null 패킷의 CC는 정의되지 않으며, 같은 PID의 연속 두 패킷이 허용된 duplicate이면 같은 CC를 사용한다. [H.222.0 §2.4.3.3](https://www.itu.int/rec/dologin_pub.asp?id=T-REC-H.222.0-199507-S%21%21PDF-E&lang=e&type=items).

재현: `TestAudit20260906TSNullPackets`, `TestAudit20260906TSDuplicatePacket`. `47 1F FF 10` + stuffing인 null 두 개와 byte-identical PAT 복제 모두 `continuity counter gap`으로 거부됐다. 수정: null PID를 먼저 제외하고, 동일 CC일 때 실제 허용 duplicate인지 확인 후 중복 payload를 처리하지 않는다. adaptation discontinuity 처리도 같은 상태기로 검증한다.

**F05 — PSI section을 TS 패킷 사이에서 조립하지 않는다.**

위치: [mpegts/reader.go:393](../internal/format/mpegts/reader.go#L393), `psiSection`.

PUSI가 없는 후속 패킷을 버리고, 첫 패킷 안에 section 전체가 없으면 UnexpectedEOF를 반환한다. PAT/PMT section은 단일 188바이트 TS 패킷을 초과할 수 있다.

재현: `TestAudit20260906TSSplitPSI`. 프로그램 50개의 PAT: section_length=209, 전체 212바이트, 정상 MPEG CRC. 첫 packet에 pointer 0과 183바이트, 다음 packet에 나머지를 배치했지만 거부됐다. 수정: PID별 bounded PSI 조립, pointer_field가 가리키는 이전 section 끝과 새 section 시작, CRC·section_length·continuity를 함께 처리한다.

**F06 — PTS wrap 경계에서 B-frame의 이전 epoch 복귀를 처리하지 못한다.**

위치: [mpegts/reader.go:479](../internal/format/mpegts/reader.go#L479), `timestampEpoch.unwrap`.

큰 값→작은 값에서 epoch를 더하지만, PTS가 decode order에서 잠시 이전 epoch의 큰 값으로 돌아오는 경우는 처리하지 않는다. DTS와 달리 PTS는 B-frame 때문에 단조 증가하지 않는다.

재현: `TestAudit20260906PTSWrapReorder`. M=2^33일 때 raw `[M-2, 2, M-1, 3]`은 `[M-2, M+2, M-1, M+3]`으로 해석돼야 한다. 세 번째 값이 17179869183으로 변해 약 **26.5시간** 앞으로 점프한다. 수정: 마지막 unwrapped clock/DTS에 가까운 modulo 후보를 선택하고 reorder와 실제 reset을 구분한다.

**F07 — 한 PES 내부의 AAC rate/config 변경을 놓친다.**

위치: [mpegts/reader.go:562](../internal/format/mpegts/reader.go#L562).

첫 ADTS frame의 config만 trackInfo에 저장한다. 이후 frame은 자기 sample rate로 basePTS를 계산하면서 최초 stream time base에 넣는다. PES 사이의 config 변경 검증이 있어도 PES 내부는 우회한다. MP3 분기에도 유사한 첫-frame-only 비교 구조가 있다.

재현: `TestAudit20260906TSInPESConfigChange`. 같은 PES에 48kHz와 44.1kHz AAC를 넣으면 stream은 48000Hz인데 두 번째 PTS가 442024가 되어 첫 PTS 480000보다 작아진다. 수정: 모든 frame의 rate/channel/profile을 최초 config와 비교하고, 변경을 지원하지 않으면 패킷을 반환하기 전에 오류 처리한다. MP3 경로는 별도 회귀 검증도 필요하다.

**F08 — raw ADTS profile 변경을 최초 ASC로 덮는다.**

위치: [open_raw.go:69](../pkg/media/open_raw.go#L69).

sample rate와 channels만 비교하고 AudioObjectType/profile은 비교하지 않는다. 재현: `TestAudit20260906ADTSProfileChange`, 같은 48kHz stereo에서 header byte2를 `4C`(LC)→`0C`(Main)로 변경해도 Open이 성공하고 LC ASC를 유지한다. 수정: config를 frame마다 비교하고 미지원 변경을 거부한다. 이는 payload 디코딩 없이 헤더만으로 확인 가능하다.

**F09 — AAC channel configuration과 채널 수를 혼동한다.**

위치: [codec_adts.go:79](../internal/core/codec_adts.go#L79), [open_raw.go:67](../pkg/media/open_raw.go#L67), [writer_config.go:28](../internal/format/mp4/writer_config.go#L28), TS AAC adapter.

configuration 7은 채널 일곱 개가 아니라 7.1의 **8채널**이다. 입력은 7채널로 보고하고, MP4 출력 검증은 정상 `Channels=8`과 configuration 7을 다르다고 거부한다. [Android의 AAC channel mapping](https://android.googlesource.com/platform/prebuilts/fullsdk/sources/%2B/refs/heads/androidx-constraintlayout-release/android-35/com/google/android/exoplayer2/audio/AacUtil.java)에서도 config index와 count를 구별한다.

재현: `TestAudit20260906AACChannelConfiguration7`, `TestAudit20260906AAC8ChannelMux`. ADTS `FF F1 4D C0 01 1F FC`는 config7, length8이며, ASC `11 B8`은 AOT2/index3/config7이다. 수정: bitstream 계층에 configuration→channel count 매핑을 두고 모든 adapter가 재사용한다. PCE와 reserved configuration의 지원 범위도 명시한다.

**F10 — Ogg의 일시적 읽기 실패가 page 경계를 잃게 한다.**

위치: [ogg/reader.go:187](../internal/format/ogg/reader.go#L187), `readPage` 호출 오류 경로.

fixed header를 읽고 lacing/body에서 실패하면 source 위치를 page 시작으로 되돌리지 않는다. 새 context로 다시 읽어도 page 중간을 새 헤더로 해석한다. 재현: `TestAudit20260906OggReadRetry`. page 시작 96, 실패 후 cursor 123. 한 번만 발생하는 DeadlineExceeded가 해제돼도 다음 ReadPacket은 UnexpectedEOF다. 수정: 한 page 읽기를 원자적으로 처리하거나 partial read 상태를 보존한다. 기존 failed-seek index rollback 테스트는 이 경로를 덮지 않는다.

**F11 — WebM의 일시적 block 읽기 실패도 element 경계를 잃는다.**

위치: [webm/demux_reader.go:314](../internal/format/webm/demux_reader.go#L314).

element header를 소비한 뒤 payload read가 실패하면 다음 호출이 payload를 element header로 읽는다. 재현: `TestAudit20260906WebMReadRetry`, 기존 RFC8794/9559 fixture의 첫 Block payload만 잠시 차단했다가 해제했는데 `element at offset 71: ebml: invalid VINT`가 됐다. 수정: element 시작/cursor와 부분 상태를 함께 복구한다. BlockGroup 내부 실패도 같은 transaction 경계로 점검한다.

**F12 — progressive MP4의 실패한 seek가 정상 재생 커서를 소모한다.**

위치: [mp4/reader.go:187](../internal/format/mp4/reader.go#L187), `findSeekIndexScaled`.

실제 trackState를 초기화·순회한 후 eligible sync sample이 없으면 오류를 반환하며 cursor를 복구하지 않는다. 재현: `TestAudit20260906FailedProgressiveSeek`. sync sample 없는 3개 샘플에서 첫 샘플 재생 후 keyframe seek를 실패시키면, 아직 두 개가 남았는데 다음 NextSample은 EOF다. 수정: 임시 cursor로 계산하고 모든 track의 seek가 성공한 경우에만 commit한다.

**F13 — HLS/DASH seek는 새 segment 준비 전에 이전 재생을 닫는다.**

위치: [hls.go:236](../pkg/media/hls.go#L236), [dash.go:317](../pkg/media/dash.go#L317).

현재 demuxer를 닫고 next/base를 바꾼 후 HTTP fetch와 nested seek를 수행한다. 실패하면 기존 재생을 계속할 수 없다. 재현: `TestAudit20260906HLSFailedSeekKeepsPosition`. 첫 segment에 패킷이 남은 상태에서 두 번째 segment가 503을 반환하는 seek를 시도하면, 이후 ReadPacket도 계속 503이며 기존 segment를 잃는다. HLS는 실행 재현했고 DASH는 동일한 코드 순서를 확인했다. 수정: 새 demuxer의 초기화·shift 계산·seek까지 성공한 뒤 교체하고 이전 것을 닫는다.

**F14 — MP4의 부족한 chunk table을 정상 EOF로 반환한다.**

위치: [mp4/stream.go:147](../internal/format/mp4/stream.go#L147).

chunk slot이 부족하면 `peekNext`가 false만 반환한다. 상위 NextSample은 손상으로 인식하지 않고 track 종료로 처리한다. 재현: `TestAudit20260906MissingChunkIsNotEOF`: stts/stsz에 샘플 2개, stsc는 chunk당 1개, stco는 하나일 때 두 번째 샘플은 오류 없이 사라진다. Remux도 성공한 것으로 종료할 수 있다. 수정: 일치하지 않는 table에 `cursorErr=ErrCorrupt`를 설정하고, uniform stsz count를 버리는 경로와 count 합계도 검증한다.

**F15 — 지연 fMP4 재생이 완료된 샘플 메타데이터를 계속 보관한다.**

위치: [mp4/reader.go:437](../internal/format/mp4/reader.go#L437), [fragment.go:291](../internal/format/mp4/fragment.go#L291).

한 fragment씩 파싱하지만 이전 `rd.fragments`를 제거하지 않는다. 재현: `TestAudit20260906FragmentPlaybackRetention`, 1-sample fragment 1000개를 모두 읽은 뒤 1000개 엔트리가 남는다. payload leak은 아니지만 긴 스트림의 메모리가 총 샘플 수에 비례한다. 수정: playback은 현재 fragment만 보관하고, seek용 sparse index 또는 요청 시 전체 index와 분리한다.

**F16 — 취소된 HTTP ReadContext가 mutex 대기에서 빠져나오지 못한다.**

위치: [source_http.go:113](../pkg/media/source_http.go#L113).

`posMu.Lock()` 뒤에서 ctx.Err를 검사한다. 첫 Read가 네트워크를 기다리는 동안 두 번째 ReadContext를 이미 취소된 context로 호출해도 mutex를 얻을 때까지 대기한다. 재현: `TestAudit20260906HTTPCanceledQueuedRead`. barrier로 첫 read를 막아 두면 두 번째 호출도 100ms 내 반환하지 않으며, 첫 read를 해제해야 완료한다.

수정: lock 전 ctx 검사로 이미 취소된 호출을 거부하고, 대기 도중 취소까지 지원하려면 context-aware operation gate를 사용한다. read/seek를 `opMu`로 직렬화하는 demuxer에도 같은 대기 패턴이 있으므로 API의 동시 호출 범위와 함께 검토한다. **Go memory data race 검출과는 다른 cancellation/progress 문제다.**

**F17 — HTTP retry가 response header 이전 오류에만 적용된다.**

위치: [source_http.go:282](../pkg/media/source_http.go#L282), [source_http.go:316](../pkg/media/source_http.go#L316).

`do` 안의 transport/429/5xx 오류는 RetryPolicy로 전달되지만, fetch의 body `io.ReadFull`에서 난 일시적 단절은 즉시 반환된다. 재현: `TestAudit20260906HTTPBodyRetry`. 첫 data response만 짧게 끊기고 다음 요청은 정상인 서버에 MaxRetries=1, always-retry policy를 지정했지만 policy 호출 횟수는 0, 결과는 UnexpectedEOF다. 수정: body 읽기까지 재시도 단위에 포함하고, offset·ETag·부분 데이터의 덮어쓰기/반환 정책을 명확히 한다.

**F18 — OpenMP4WithInit의 오류 chain이 일반 Open과 다르다.**

위치: [open_mp4.go:40](../pkg/media/open_mp4.go#L40).

`fmt.Errorf("%w: %v", ErrInvalidData, err)`에서 underlying error는 문자열만 남는다. 재현: `TestAudit20260906InitErrorChain`, 반환 문자열에 deadline이 보여도 `errors.Is(err, context.DeadlineExceeded)`는 false다. HLS/DASH의 separate-init fMP4 경로에도 영향을 준다. 수정 예: `fmt.Errorf("%w: %w", ErrInvalidData, err)` 또는 `errors.Join`.

**F19 — manifest timestamp shift의 왕복 변환이 exact tick을 잃는다.**

위치: [hls.go:556](../pkg/media/hls.go#L556), [hls.go:578](../pkg/media/hls.go#L578); DASH가 공유한다.

anchor tick을 ns로 절삭하고, 음수 shift를 다시 tick으로 절삭한다. 48kHz에서 anchor 1024 → 21333333ns → shift -1023ticks이므로 0으로 옮기려던 첫 PTS가 1이 된다. 재현: `TestAudit20260906ManifestExactOrigin`의 HLS/DASH 모두 PTS=1. 수정: 각 stream의 anchor를 exact rational/ticks로 유지하고 offset을 한 번만 변환한다. 선택 stream seek의 비교 기준과 결과 시각도 동일한 표현을 사용해야 한다.

**F20 — HLS implicit range가 잘못된 과거 range를 이어 쓴다.**

위치: [manifest/hls.go:286](../internal/manifest/hls.go#L286).

range 없는 segment를 처리할 때 previousRangeURI/End를 초기화하지 않는다. `a.mp4 range 4@0 → b.mp4 전체 → a.mp4 range 4`를 offset4로 허용하지만 직전 segment가 같은 resource의 subrange가 아니므로 parse에 실패해야 한다. [RFC8216 §4.3.2.2](https://www.rfc-editor.org/rfc/rfc8216.html#section-4.3.2.2).

재현: `TestAudit20260906HLSImplicitRangeAfterWholeSegment`. 수정: 바로 직전 segment의 range만 기억하고 non-range segment에서 상태를 지운다.

**F21 — 유효한 AV1 maximum-parameters level을 거부한다.**

위치: [av1/config.go:25](../pkg/bitstream/av1/config.go#L25).

`seq_level_idx > 23`을 전부 거부하지만 24–30과 달리 31은 Maximum parameters다. [AV1 Annex A](https://github.com/AOMediaCodec/av1-spec/blob/master/annex.a.levels.md?plain=1).

재현: `TestAudit20260906AV1MaximumLevel`, config `81 1F 0C 00`이 거부된다. 수정: reserved 24–30만 거부하고 31의 지원 여부를 규격 유효성과 분리한다.

**F22 — AV1 fixed field 간 bit-depth 제약을 검증하지 않는다.**

위치: [av1/config.go:23](../pkg/bitstream/av1/config.go#L23).

profile/level/일부 reserved bits만 검사하고 byte2의 profile-dependent 조합은 확인하지 않는다. 재현: `TestAudit20260906AV1InvalidBitDepth`, `81 00 2C 00`은 profile0, high_bitdepth=0인데 twelve_bit=1이며 검증을 통과한다. 존재하지 않는 twelve_bit는 0이어야 한다. [AV1 ISOBMFF §2.3.4](https://aomediacodec.github.io/av1-isobmff/#av1codecconfigurationbox-semantics).

수정: profile·bit depth·monochrome·chroma subsampling·tier의 조합을 공유 validator에서 검사한다. configOBU Sequence Header와 fixed record의 일치 여부는 추가 검증 범위로 남아 있다.

**추가 정적 후보 — 위 22개 재현 문제에 포함하지 않음**

1. `mp4.Reader.NextSample`의 `make([]byte, s.size)`에는 public packet byte cap이 없다. 공격자가 선언한 uint32 sample size가 그대로 할당 요청이 된다. F02를 고쳐도 packet payload 예산이 별도로 필요하다. 실제 수 GiB 할당 시험은 하지 않았다.
2. `parseStsd`는 첫 sample entry만 읽고 나머지를 건너뛰며 `stsc.sampleDescIndex`와 `tfhd.descriptionIndex`를 sample config 선택에 사용하지 않는다. 여러 description을 쓰는 정상 MP4의 설정 전환을 구현하거나 명시적으로 거부해야 한다. 전체 다중-description fixture 재현은 미실시다.
3. `indexFLACFrames`는 모든 바이트 위치에서 sync/header CRC8 후보를 찾으며 frame CRC16/연속 frame number로 경계를 검증하지 않는다. 압축 payload 안의 우연한 header 후보를 실제 frame으로 오인할 가능성을 실물 fixture로 검증할 필요가 있다. 이번에는 발생 확정으로 분류하지 않았다.
4. MPEG-TS `initializeTracks`는 최초 tracks 등록 이후 PMT 갱신을 반영하지 않는다. PID 추가·삭제·codec 변경을 지원하지 않는다면 조용히 이전 map을 쓰기보다 명시적 오류가 필요하다. PMT version 변화 전체 시나리오는 별도 테스트 대상이다.
5. 출력 writer의 중간 I/O 오류는 여러 backend에서 영구 실패 상태로 고정되지 않는다. 일부 bytes가 나간 뒤 재시도/Close가 다시 header/fragment를 쓰는 경로를 fault injection으로 검증해야 한다. 기존 short-write 검사는 이후 재호출의 파일 유효성까지 보장하지 않는다.
6. manifest resource의 모든 새 요청에 같은 `Header`를 복제한다. untrusted manifest가 다른 origin의 absolute URI를 제공할 때 Authorization 등 전달 정책을 caller가 설정할 수 있어야 한다. 현재 사용자가 준 header를 공통 적용하는 API이므로 이를 검증된 유출 사건으로 세지 않았다. origin-aware RoundTripper/allowlist 또는 resource별 header callback이 개선안이다.

**미구현·지원 제한 — 문서상 정책인 부분은 버그로 세지 않음**

- HLS master의 외부 AUDIO rendition은 선택한 video URI를 대체한다. video+외부 audio를 동시에 demux/merge하는 일반적 adaptive A/V 조합은 제공하지 않는다.
- DASH는 하나의 representation만 선택한다. multi-Period, ABR 전환, 복수 adaptation-set A/V 병합은 제공하지 않는다. dynamic MPD 전체 timing 모델이나 모든 segment addressing 형태를 지원한다고 볼 수 없다.
- HLS는 AES-128을 처리하지만 SAMPLE-AES/DRM/LL-HLS part ingestion은 구현돼 있지 않다.
- Ogg public adapter는 Opus 중심이며 Ogg Vorbis/FLAC·chained logical stream 전체 지원으로 확대 해석하면 안 된다.
- TS는 188-byte packet 입력을 전제로 한다. `.m2ts` 확장자 선택이 192-byte M2TS framing 구현을 뜻하지 않는다. multi-program selection API와 위 F05의 PSI 조립도 필요하다.
- `Remux`는 framing converter가 아니다. TS AAC는 raw AAC로 demux되므로 TS로 되돌릴 때 ADTS 재포장이 필요하며 현재 직접 remux 정책은 거부한다. NAL length-prefix/Annex-B 변환도 호출자가 별도 처리해야 한다.
- MP4의 fast-start 출력, 일반 metadata 쓰기, 일부 disposition/trim 표현, 자막·DRM 등은 현재 명시된 범위 밖이다. 미지원 metadata/DiscardPadding의 오류 반환은 조용히 손실시키는 결함과 구별한다.
- 순수 sequential source에서 자동 탐색 후 바로 처리하는 형식은 MPEG-TS다. WebM/Ogg에는 이미 받은 prefix를 되감을 수 있는 spool이 필요하며, separate-init `OpenMP4WithInit`에는 일반 Open의 MaxInitBytes/OnOpen 옵션이 없다.

**테스트 품질 및 다음 수정 순서**

인터페이스 계층 분리, exact rational 비교, packet 소유권, MP4 독립 parser 검증과 기존 사양 기반 boundary suite는 잘 갖춰져 있다. 다만 “정상 test/race 통과”를 다음 조합의 검증으로 대신할 수 없다: 실패한 작업 뒤 재개, modulo wrap과 reorder의 결합, 한 PES 안의 여러 config, 작은 선언값에 의한 메모리 확장, picture가 아닌 입력만 이어지는 라이브 상태.

수정 순서는 F01–F04를 먼저 처리하고, F10–F14/F16의 실패 복구·취소, F05–F09/F18–F22의 형식·시각 정확성, F15와 성능 후보 순서가 적절하다. 특히 default buffer 값만 조정해서 F02/F03을 해결한 것으로 처리하면 안 된다. 사양의 정상 예외(null/duplicate/AV1 level31)와 비정상 입력 거부를 같은 회귀 모음에 둬야 한다.

작성자 확인 없이는 확정할 수 없는 제품 선택은 multi-representation 지원, 실패한 seek의 원자성 범위, origin별 인증 정책이다. 이번 감사에는 사용자 답변이 필요한 차단 요인은 없다. 해당 선택과 무관하게 먼저 고칠 수 있는 재현 문제가 위에 명시돼 있다.
