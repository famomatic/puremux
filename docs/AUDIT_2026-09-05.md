# Puremux 전체 코드 감사 — 2026-09-05

> **수정 후 상태 — 2026-09-05, Codex `/root`**
> 아래 본문은 수정 전 감사 기록이다. 당시 실패한 15개 top-level 회귀 테스트(13개 원인)는 현재 모두 통과한다.
> 수정·검증·지원 범위의 최신 내용은 [수정 결과](AUDIT_FIXES_2026-09-05.md)를 참조한다.
> 기존 cache overlay는 수정 전 재현 자료이며 현재 검증에는 사용하지 않는다.


작성: Codex `/root`. 요청 범위: 경계값, 동시성, 기능 오작동·누락, 성능·구조 개선.

**판정: 수정 필요.** 기존 전체 테스트와 race 검사는 통과하지만, 추가 감사 테스트 15개에서 13개 원인의 문제를 재현했다. HLS/DASH 공통 구현의 중복 실패는 한 원인으로 집계했고, EOF 재읽기와 라이브 재시도 실패도 같은 상태 전이 문제로 묶었다. 제품 코드는 수정하지 않았다.

**검증 범위와 한계**

- 공개 media API, live/preprocessor, HTTP·HLS·DASH, MP4·MPEG-TS·Ogg·EBML 연결 경로와 관련 테스트를 검토했다. 코덱 설정 변환과 기존 사양 검증 기록도 대조했다.
- MSYS2 UCRT64에서 `CGO_ENABLED=0 go test -count=1 ./...`, `CGO_ENABLED=0 go vet ./...`, `CGO_ENABLED=1 go test -race -count=1 ./...`가 통과했다. 캐시는 `F:/cache`를 사용했다.
- 아래 재현 테스트는 의도한 계약을 assertion으로 작성했으며 **현재 구현에서는 실패한다**. 수정 완료나 통과 테스트로 간주하면 안 된다.
- 테스트 소스·Go overlay·실행 로그는 `F:/cache/puremux-audit-20260905/`에 보관했다. 저장소의 제품·기존 테스트 파일은 변경하지 않았다.
- wire 형식은 기존 사양 기반 fixture를 재사용했다. 새 Ogg EOS 사례는 RFC 7845 §4.4에서 직접 유도했다. AAC ASC `11 90`은 MSB-first AOT=2, frequency index=3, channel config=2이며, Ogg granule·OpusHead는 little-endian이다. MP4 empty stss는 big-endian FullBox version/flags=0, entry_count=0이다. 압축 payload는 불투명 데이터로 취급했고 디코딩하지 않았다.
- 전체 분기·모든 실제 코덱 파일에 대한 완전성 증명은 아니다. 이번에 fuzz mutation을 새로 실행하거나 모든 플랫폼을 재빌드하지는 않았다. 아래 정적 검토 항목은 런타임 재현 항목과 구분했다.

**재현된 문제 — P1은 우선 수정, P2는 후속 수정**

1. **[P1] HLS/DASH가 일시적인 세그먼트 부재에서 복구하지 못한다.**
   위치: `pkg/media/hls.go:170`, `pkg/media/dash.go:204`.
   현재 세그먼트를 닫고 next를 진행시킨 뒤 refresh한다. refresh가 `ErrNoNewSegments` 또는 네트워크 오류를 반환하면 current는 닫힌 상태다. 다음 ReadPacket은 refresh를 재시도하지 않고 current를 읽어 `ErrClosed`로 끝난다. 정상 VOD EOF를 두 번 읽어도 두 번째는 EOF 대신 ErrClosed다.
   재현: `TestAuditManifestRetryAfterNoNewSegments`의 HLS/DASH 두 경우에서 새 세그먼트를 게시한 뒤에도 `media: closed`; `TestAuditManifestEOFStable`도 같은 오류.
   수정: active/waiting/ended 상태를 구분하고 세그먼트 종료 정산을 한 번만 수행한다. waiting 상태에서는 refresh/open을 재시도하고 ended 상태에서는 계속 EOF를 반환한다. seek·다음 세그먼트 open 실패 후 복구도 같은 상태 기계로 처리한다.

2. **[P1] DASH Close가 진행 중인 ReadPacket과 교착할 수 있다.**
   위치: `pkg/media/dash.go:164`, `pkg/media/dash.go:366`, `pkg/media/dash.go:391`.
   ReadPacket이 opMu를 잡은 채 current.ReadPacket을 호출한다. Close는 root를 취소한 뒤 opMu를 기다려야 current.Close를 호출한다. SingleFile의 HTTPSource는 별도 root를 쓰므로 상위 root 취소만으로 그 HTTP 읽기가 취소되지 않는다. 읽기는 current.Close를 기다리고 Close는 읽기 종료를 기다릴 수 있다.
   재현: `TestAuditDASHCloseUnblocksRead`. Close로 해제되는 mock demuxer를 사용했으며, 100ms 내 종료하지 못했다. 테스트 종료 시 mock을 직접 닫아 모든 goroutine을 회수했다.
   수정: 각 작업 context에 wrapper root 취소를 연결한다. 또는 current의 소유권·교체를 동기화한 뒤, opMu 확보 전에 안전하게 current.Close를 호출할 수 있도록 재설계한다. 데이터 race 탐지 통과는 이 교착을 보장하지 않는다.

3. **[P1] live jitter 버퍼가 포화되면 정상 입력도 계속 버리고 출력하지 않는다.**
   위치: `internal/preprocessor/enforcer.go:77`, `internal/preprocessor/enforcer.go:95`.
   초과 시 가장 오래된 패킷을 먼저 버린 뒤 시간 창 조건으로만 flush한다. 보유 가능한 패킷들의 시간 범위가 JitterWindow보다 작으면 가장 오래된 패킷이 영원히 flush 조건에 도달하지 않는다.
   재현: `TestAuditLiveBufferSaturationMakesProgress`. MaxBufferPackets=2, JitterWindow=400ms, 48kHz/1024-sample 간격의 정상 패킷 100개에서 출력 0개, overflow drop 98개. MaxBufferPackets=1도 허용되지만 Close 전 출력이 불가능하다. 기본 64개도 충분히 높은 패킷률에서는 같은 문제가 생긴다.
   수정: 포화 시 안전한 가장 오래된 패킷을 먼저 방출하거나, 허용 가능한 설정·포화 정책을 명시해 진행을 보장한다. 키프레임 유실도 함께 검증한다.

4. **[P1] Ogg Opus EOS trimming이 패킷 시작 시각을 앞당긴다.**
   위치: `internal/format/ogg/reader.go:186`, `pkg/media/open_ogg.go:86`.
   마지막 page도 `start = granule - 전체 packet duration`으로 역산한다. 그러나 EOS granule은 마지막 패킷의 끝부분 제거를 표현할 수 있다. 이전 page granule을 기준으로 시작 시각을 유지해야 한다. 공개 adapter에는 제거량을 DiscardPadding으로 전달하는 경로도 없다.
   재현: `TestAuditOpusEndTrimmingDoesNotShiftPacketStart`. 이전 granule=960, 마지막 granule=1440, 마지막 Opus packet=960 samples이면 시작은 960이고 tail trim은 480이다. 실제 시작은 480으로 반환되어 앞 패킷과 겹친다.
   수정: 이전 completed-page granule과 연속 packet clock을 유지하고, 종료 제거량을 별도 메타데이터로 전달한다. 첫 audio page가 EOS인 특수 경우도 검증한다. 근거: [RFC 7845 §4.4–4.5](https://www.rfc-editor.org/rfc/rfc7845.html#section-4.4).

5. **[P1] MP4 edit-list 지연이 PTS에만 적용되어 DTS와 시간축이 달라진다.**
   위치: `internal/format/mp4/stream.go:104`, `internal/format/mp4/fragment.go:286`.
   presentationShift를 PTS에만 더한다. 공개 API의 stream TimeBase를 공유하는 PTS/DTS가 실제 composition offset 외에 트랙 시작 지연만큼 벌어진다. DTS 기반 Remux의 트랙 병합과 후속 컨테이너 타이밍에 영향을 준다.
   재현: `TestAuditProgressiveTrackDelayDTS`. AAC 두 트랙의 시작 DTS/PTS를 각각 0, 48000으로 기록했다. 두 번째 트랙을 다시 읽으면 DTS=0, PTS=48000이다. 오디오는 원래 PTS=DTS였다.
   수정: 공개 패킷이 media timeline인지 movie timeline인지 일관되게 정의하고 edit 적용 시 DTS/PTS 관계와 트랙 간 지연을 함께 보존한다. 첫 DTS가 0인 단일 트랙 round-trip만으로 검증하지 않는다.

6. **[P1] MP4의 비어 있는 stss를 모든 sample이 keyframe인 것으로 해석한다.**
   위치: `internal/format/mp4/stream.go:149`, `internal/format/mp4/boxes.go:49`.
   stss 부재와 존재하지만 entry_count=0인 경우를 `len(t.stss)==0`으로 합친다. 전자는 all-sync지만 후자는 sync sample이 없는 경우다. 잘못된 seek 진입점과 live keyframe-first 통과를 만들 수 있다.
   재현: `TestAuditEmptySTSSIsNotAllSync`. 자체 progressive writer가 non-keyframe 하나와 empty stss를 기록한 뒤 reader가 Keyframe=true를 반환한다. 테스트에서 empty stss의 실제 bytes도 확인한다.
   수정: hasSTSS를 별도로 보유하고, stss가 없을 때만 all-sync로 처리한다. empty stss의 기본 seek는 eligible sync sample 부재를 반환해야 한다. [Apple sync sample atom 설명](https://developer.apple.com/documentation/quicktime-file-format/sample_table_atom/sync_sample_atom)도 keyframe 표의 역할을 명시한다.

7. **[P1] 자체 생성한 MPEG-TS 영상도 TS로 remux하지 못한다.**
   위치: `internal/format/mpegts/reader.go:717`, `pkg/media/open_mpegts.go:88`, `pkg/media/mux_mpegts.go:76`.
   영상 PES에서 Duration이 0으로 남는다. 공개 adapter는 이를 KnownTimestamp(0)으로 표시하고, 출력 muxer는 positive duration을 요구해 거부한다. validateRemuxFraming이 허용한 TS/H.264 경로도 실제로는 첫 영상 패킷에서 실패한다.
   재현: `TestAuditTSVideoIdentityRemux`. 기존 사양 기반 H.264 fixture로 TS를 생성한 뒤 TS 출력 Remux를 호출하면 `media: write input 0 packet: media: invalid data`.
   수정: 알 수 없는 duration을 known zero로 표시하지 않는다. PES/AU 경계와 시간 정보를 바탕으로 합법적으로 얻을 수 있는 duration을 demux 단계에서 결정하거나, duration이 wire에 필요 없는 TS serializer의 입력 계약을 분리한다. 마지막 frame duration을 임의로 추정해 exact remux라고 표시하지 않는다.

8. **[P2] MP4 → WebM/Matroska의 Opus·FLAC 설정 변환이 빠져 있다.**
   위치: `pkg/media/mux_ebml.go:114`, `pkg/media/mux_ebml.go:196`.
   반대 방향은 변환하지만 EBML은 OpusHead만 허용하며 dOps를 변환하지 않는다. FLAC 역시 raw STREAMINFO/native fLaC만 처리하고 MP4 reader가 돌려주는 dfLa를 거부한다. 코덱이 양쪽 지원표에 있어도 이 방향 remux는 실패한다.
   재현: `TestAuditMP4OpusToWebM`, `TestAuditMP4FLACToMatroska`. 각각 `Opus requires OpusHead`, `invalid FLAC codec initialization`.
   수정: codec-config 정규화 계층에서 dOps→OpusHead, dfLa→STREAMINFO→Matroska private를 제공하고 양방향 변환 표로 테스트한다. 이는 payload 디코딩이나 framing 변경이 필요 없는 작업이다.

9. **[P2] HLS/DASH seek가 non-zero segment origin을 잘못 변환한다.**
   위치: `pkg/media/hls.go:237`, `pkg/media/dash.go:318`.
   읽기에는 shiftNS를 적용하면서 seek에는 manifest segment start만 뺀다. 원본 segment timestamp가 0이 아니면 서로 다른 좌표계다. 반환값도 실제 반환 패킷과 불일치한다.
   재현: `TestAuditManifestSeekNonzeroOrigin`. 48kHz segment의 첫 timestamp=480000, 목표=1024. 기대 seek result/packet PTS/payload ID=1024/1024/2, 실제=480000/0/1. HLS와 DASH 모두 동일하다.
   수정 예: `sourceTarget = globalTarget - shift`, `globalActual = sourceActual + shift`. shift는 요청 stream time base로 정확하게 변환하고 checked arithmetic을 적용한다.

10. **[P2] MP4 exact-tick seek 결과가 한 tick 작아진다.**
    위치: `pkg/media/open_mp4.go:154`, `pkg/media/open_mp4.go:173`.
    ticks→nanoseconds→ticks 왕복 과정에서 두 번 절삭한다. 48kHz의 1024 ticks는 정수 nanosecond로 정확히 표현되지 않아 다시 ticks로 변환하면 1023이다.
    재현: `TestAuditMP4SeekExactTick`. 실제 선택한 packet PTS=1024인데 SeekResult.Timestamp=1023.
    수정: reader에 exact-tick seek/결과 경로를 제공한다. 나노초 API는 편의 경계에만 두고, 특히 1GHz보다 세밀한 허용 timescale에서는 선택 비교도 exact rational로 수행한다.

11. **[P2] HTTP redirect 뒤 manifest의 상대 URL을 잘못 해석한다.**
    위치: `pkg/media/hls.go:314`, `pkg/media/dash.go:96`.
    fetch는 body만 반환하고 최종 `resp.Request.URL`을 버린다. parser는 최초 요청 URL로 상대 URI를 해석한다.
    재현: `TestAuditManifestRedirectBase`. `/start`→`/dir/index`로 redirect되고 segment가 `s.mp4`인 경우 `/dir/s.mp4` 대신 `/s.mp4`를 요청하여 HLS/DASH 모두 404.
    수정: 최종 response URL을 body와 함께 반환해 manifest base 및 refresh URL에 적용한다. 근거: [RFC 3986 §5.1.3](https://www.rfc-editor.org/rfc/rfc3986.html#section-5.1.3).

12. **[P2] MP4 edit-list의 시간 단위 변환이 uint64 곱셈에서 overflow한다.**
    위치: `internal/format/mp4/reader.go:472`.
    `editLeadMovie * timescale / movieTimescale`은 최종 값이 작아도 중간 곱셈이 overflow한다. 자체 writer가 movieTimescale=1e9를 쓰므로 특이한 최대 정수만의 문제가 아니다.
    재현: `TestAuditProgressiveLongTrackDelayOverflow`. 48kHz 트랙의 5일 지연은 20736000000 ticks여야 하지만 2289255926으로 읽힌다.
    수정: 기존 checked rescale 함수를 재사용하고 presentationShift 누적과 PTS 합산에도 overflow 검사를 적용한다.

13. **[P2] MP4 Open이 mdat 전체를 읽어 HTTP random access 이점을 없앤다.**
    위치: `internal/format/mp4/reader.go:358`, `internal/format/mp4/boxes.go:159`.
    mdat을 건너뛸 때 seek하지 않고 io.CopyN으로 모두 읽어 버린다. HTTPSource에서는 파일 전체가 Range 요청으로 다운로드된 다음 ReadPacket에서 payload를 다시 읽는다. moov-at-end뿐 아니라 앞에 moov가 있는 파일도 영향을 받는다.
    재현: `TestAuditMP4OpenReadsMDAT`. 첫 sample 요청 전 1,049,212-byte 파일의 1,049,212 bytes를 전부 읽었다.
    수정: seekable reader에서 확인된 source/box 경계 안으로 Seek하고, 구조·샘플 offset 검증과 payload 실제 읽기를 분리한다. 큰 원격 파일에서 bytes-read와 request-count를 성능 회귀 기준으로 삼는다.

**추가 정적 검토 사항 — 아직 독립 실행 테스트로 확정하지 않은 경로**

- **자원 상한의 빈틈.** `internal/format/mpegts/reader.go:75,259`: PMT가 예고한 오디오 설정을 기다리는 동안 다른 트랙의 pending packet 전체를 누적하며, 전체 pending bytes/packets 상한은 없다. 비어 있는 오디오 트랙과 이미 쌓인 영상이 함께 EOF에 도달하는 경우 ready가 계속 false인 경로도 별도 검증이 필요하다. `internal/format/ogg/reader.go:402`: page 상한은 있지만 여러 page에 걸친 partial packet 누적 상한은 없다. `pkg/media/hls.go:395`: 새로운 EXT-X-MAP URI마다 initCache가 늘어나며 eviction/전체 byte 상한이 없다. 장기 라이브·비정상 입력에 대해 각각 aggregate budget이 필요하다. 실제 OOM을 일으키는 시험은 수행하지 않았다.
- **코덱 detector 중복과 유효성 검사 불일치.** `internal/format/mpegts/reader.go:744`의 annexBKeyframe은 core detector를 쓰지 않고 NAL type만 확인한다. HEVC `28 00`처럼 temporal_id_plus1=0인 헤더도 type만으로 keyframe으로 판단하는 경로가 보인다. core에는 해당 금지값 검사가 이미 있다. 공유 interface 뒤로 이동하고 같은 사양 byte suite를 실행해야 한다.
- **메타데이터 보존 누락.** `pkg/media/mux_mp4.go:74`, `pkg/media/mux_ebml.go:140`: Language, Disposition, stream Metadata를 output track으로 전달하지 않는다. `pkg/media/remux.go`도 source Info.Metadata를 출력으로 전달할 API가 없다. 다국어 트랙의 언어·기본 선택·제목을 보존하려면 output 모델 확장이 필요하다.
- **MP4로 출력할 때 discard padding 누락.** `pkg/media/mux_mp4.go:170`은 Packet.DiscardPadding을 OutputSample에 전달하지 않는다. Matroska/Opus 등의 정확한 끝부분 제거 의미를 잃을 수 있다. 지원 가능한 MP4 edit/trim 표현으로 변환하거나 지원 불가를 명시해야 한다. 위 Ogg demux 자체의 EOS 오류와는 별도 출력 단계다.
- **파일 설치 실패 복구의 오류 손실.** `pkg/media/remux.go:316` 이후 fallback은 backup 복구 os.Rename 오류를 버린다. 실패 반환 시에도 기존 outputPath가 없고 backup만 남을 수 있는 경로다. OS/filesystem fault injection으로 검증하고, 복구 오류와 backup 경로를 함께 반환하는 편이 좋다. 이번 감사에서 파일 손실을 실제로 유발하지 않았다.

**최적화·개선 포인트**

- `internal/format/mp4/writer_fragmented.go:182`: audio packet마다 pendingDuration이 전체 pending을 순회하여 fragment 하나에 O(N²) 비교가 발생한다. 현재 fragment의 min DTS/max end를 증분 유지할 수 있다.
- `internal/format/mp4/writer_fragmented.go:214`: flush에서 payload→track별 mdatPayload→outputBox mdat으로 fragment 크기의 복사가 반복된다. header와 이미 보유한 payload 범위를 순서대로 쓰면 peak memory와 copy를 줄일 수 있다.
- 같은 writer의 MaxFragmentBytes는 payload 길이만 센다. pending metadata, bytes.Buffer 여유 capacity, flush 복사본까지 포함한 전체 메모리 상한은 아니다. 작은 packet 다수에 대한 MaxFragmentPackets/metadata budget과 대형 pooled buffer 폐기 기준이 필요하다.
- `internal/format/mp4/fragment.go:109`: moof마다 지금까지 모은 fragments 전체를 재정렬한다. 전체 parse 종료 시 한 번 정렬하거나 정렬된 run을 병합할 수 있다.
- `internal/format/mp4/reader.go:154`: progressive seek는 여러 번의 전체 sample cursor 순회가 필요하다. stts run prefix·chunk prefix·sync index로 탐색 비용을 줄일 수 있다.
- `internal/format/mpegts/reader.go:295`: seekable TS를 통째로 읽고 PES와 개별 payload를 다시 복사·보관한다. 파일 크기에 비례한 여러 복사본 대신 source offset 기반 index와 lazy read가 장시간 녹화에 적합하다.
- `pkg/media/source_http.go:112`: 작은 Read마다 별도 HTTP Range 요청이다. 구조 parser와 raw frame scanner의 작은 read를 합치는 bounded read-ahead cache가 필요하다. 데이터 변경 검사와 ReaderAt 병렬성은 유지해야 한다.
- `pkg/media/open_ogg.go:85`: 내부 reader가 소유권을 넘긴 packet bytes를 adapter가 한 번 더 복사한다. 재사용 계약을 확인한 뒤 소유권 이전으로 제거할 수 있다.
- fMP4 FragmentDuration은 영상에서 시간 기준으로 작동하지 않고 keyframe마다 cut한다. 현재 GOP 정책의 의도는 인정하되 옵션 설명에 audio-only 의미와 byte-limit 강제 분할 시 non-keyframe fragment 가능성을 명시하는 편이 좋다.

**현재 미지원·제한 범위 — 결함과 구분해야 할 항목**

- HLS master에서 AUDIO rendition URI가 있으면 선택한 video URI를 그 audio URI로 교체한다(`pkg/media/hls.go:352`). 기존 주석·테스트가 이 오디오 우선 정책을 명시한다. 따라서 일반적인 영상+외부 오디오 HLS를 하나의 Demuxer로 병합하는 기능은 현재 없다. [RFC 8216 §4.3.4](https://www.rfc-editor.org/rfc/rfc8216.html#section-4.3.4)의 rendition group을 모두 읽는 기능과는 구분해야 한다.
- DASH는 한 representation만 선택하고 기본값도 오디오 우선이다. 별도 audio/video AdaptationSet 병합은 제공하지 않는다.
- DASH multi-Period, 종료 경계가 없는 dynamic SegmentTimeline의 r=-1, wall-clock 기반 duration-template live 선택은 미지원 또는 제약이 있다(`internal/manifest/dash.go:150,332,361`). single Period의 start 속성도 XML 모델에 없다. [DASH-IF timing model](https://dashif.org/Guidelines-TimingModel/)에 맞춘 범위 확대가 필요하다.
- Remux는 elementary framing 변환기가 아니다. MP4/WebM→TS, TS AAC→TS는 현재 framing 정책상 거부한다. 이것과 위 TS 영상 Duration=0 실패는 별개다.
- LiveMuxer에 stream별 종료/idle watermark API가 없어 트랙 하나가 멈추면 다른 트랙이 interleave 상한에 도달할 수 있다. ErrLiveBufferFull은 의도된 제한이지만 트랙 교체·동적 종료에는 별도 API가 필요하다.
- Ogg는 Opus 중심이고 non-seekable Open은 MPEG-TS만 지원한다. MP4에서 VP8/Vorbis/MP3/subtitle, CENC/DRM, fast-start relocation, manifest 생성은 현재 릴리스 범위 밖이라고 문서에 명시되어 있다.

**수정 순서 및 재검증**

먼저 1–7번의 진행 정지·교착·패킷 의미 오류를 처리한 뒤 8–12번의 상호운용·탐색·산술 문제를 처리한다. 13번은 큰 원격 파일을 사용하는 경우 앞당길 가치가 있다. 이후 자원 상한과 메타데이터 계약을 정하고 성능 최적화를 진행한다.

잘 구성된 부분: codec-config 검사와 container adapter 분리가 대체로 유지되고, checked rational arithmetic·packet 소유권·독립 mp4ff parser 검증·사양 기반 boundary test가 이미 있어 회귀 테스트를 추가하기 좋은 구조다. 문제는 이 검증이 manifest 재시도, 지연된 트랙, empty stss, EOS trimming 같은 조합을 아직 덮지 못한다는 점이다.

사용자에게 추가 결정을 받아야만 확정할 수 있는 런타임 발견 사항은 없다. 지원 범위 확대는 별도의 제품 선택이다. 이번 요청은 감사이므로 결함 수정·커밋·배포는 하지 않았다.
